# Eight-player networking implementation decisions

## Assumptions

- Steam is the normal launch mode. The explicit `-localNetworking` process argument selects temporary development networking and skips Steam API, Steam Input, callbacks, identity, lobby, and overlay initialization. Launch the Unity Editor itself with this argument for local editor sessions.
- Solo uses GameTransport loopback with an OS-assigned port, including on normal Steam launches. Steam availability does not gate solo play.
- MainMenu and Game remain the enabled build scenes. Lobby UI belongs to MainMenu and the persistent SessionRoot; there is no lobby scene.
- Each Steam peer uses a distinct account/device. Local process names are connection-scoped `Player N` labels. Steam names are display information, not reconnect identity; no account or inventory persistence is introduced.
- Local development uses a loopback address and selected port by default, while retaining a typed IPv4 guest endpoint. The menu's LAN-address discovery/share picker is removed; the overlay shares the loopback endpoint for multiple local processes. The existing EndpointUtility LAN-discovery helper is legacy code outside this flow.
- The existing four-seat cart remains unchanged in capacity. A second scene cart and consistent inter-cart collision rules remain separate work.
- Eight players and 64 simultaneously thrown items are the target workload, not a new item-count restriction. The Ryzen 5 3600 and GTX 1080/RTX 2080 targets remain performance acceptance requirements, not established minimum specifications.

## Transport and platform decisions

- FishySteamworks C# sources are pinned to [`0320459da446a95fc109aef66d42e1337e3b5fff`](https://github.com/FirstGearGames/FishySteamworks/tree/0320459da446a95fc109aef66d42e1337e3b5fff) in `Assets/Plugins/FishySteamworks`, with its MIT license. This avoids replacing vendored FishNet 4.7.3 or its cart motion extension. The installed Steamworks.NET package supplies the Steam API.
- Add `GameSteamTransport`, which inherits FishySteamworks and adds the same development payload counters as GameTransport. This replaces the plan's plain FishySteamworks component assignment. Existing diagnostics select the active transport's counters; these count application payload, including host loopback traffic, and exclude wire overhead and retransmissions.
- FishySteamworks defaults to P2P and seven remote guests. Its maximum-client setter also updates the field used by startup. Multipass keeps a stable two-child list, uses `GlobalServerActions = false`, and starts/stops only the selected listener. FishNet admission independently limits total membership to eight, or one for solo.
- The pinned transport's background timeout thread and finalizer are removed: session deadlines and Unity lifecycle teardown own those responsibilities. Server shutdown closes remote Steam sockets, clears queued host packets, and recycles delivered host packet arrays. Socket/listener guards ignore callbacks from old transport attempts. These are additional dependency adaptations needed for repeated sessions and cancellation; preserve them when updating the pin.
- Normal callback pumping and Steam Input lifetime belong to `SteamLifetime`. Steam initializes once at application startup; if it is unavailable, start Steam and restart the game for multiplayer. The HUD's shared glyph provider owns only textures and uses existing text fallbacks when Steam Input is unavailable.
- `steam_appid.txt` at the repository root remains the single development App ID configuration (`480`). A recurring Windows development-build callback copies this file beside the executable. Replace the source value when assigning the game's App ID; release launch/depot configuration must use that App ID. Closed-game Steam invitations depend on Steam launching the configured executable with `+connect_lobby`; App ID 480 does not register Two Birds as its own Steam product.

## Lobby, readiness, and shutdown decisions

- Steam lobbies are friends-only with eight members and metadata keys `game`, `protocol`, `host`, and `phase`. The game identifier is `two-birds`; the initial wire-compatibility identifier is `eight-player-1`. Increment the protocol for incompatible networking changes. Both Steam lobby entry and FishNet admission check compatibility.
- Friends' results come from the user's friends currently reporting a lobby for the active Steam App ID, followed by game/protocol checks. There is no public lobby browser. Invitations are available before and during play. [Steam lobby semantics](https://partner.steamgames.com/doc/features/multiplayer/matchmaking) supply discovery/membership; FishNet supplies gameplay admission and readiness.
- Every admitted member gets a reliable admission message before FishNet's scene load path. Lobby snapshots are sent on membership/readiness changes. Start requires the admitted host and, for Steam multiplayer, a created lobby; there is no ready vote or minimum guest count.
- An admitted lobby has no load deadline. Steam lobby creation still has a connection deadline. Start and late admission to a loading/playing game establish a fresh load deadline. Lobby metadata stays joinable during loading when space remains, so FishNet can route late arrivals through its global-scene acknowledgements.
- Local-player initialization and world readiness are separate gates. Guest baseline start/completion echo the requesting client's session ID and carry the world epoch; completion follows all reliable records, including an empty baseline. Host/solo signal readiness directly after world initialization. Input enables only when both gates finish.
- Steam async operations capture the current attempt. Canceled results cannot start networking; successful stale joins/creates leave the returned lobby unless it is already the current lobby. New invitations queue until transport teardown and outstanding Steam lobby callbacks finish. Waiting for those callbacks also prevents a canceled join from leaving a newer join to the same lobby; cancellation can remain in Stopping until Steam returns its result. Invalid Steam API-call handles fail immediately. The original host ID remains fixed; Steam ownership transfer does not migrate gameplay.
- Leave first marks the session stopping and closes lobby membership. Network teardown waits for in-flight scene work, sends and flushes disconnect notifications, stops the local client, and stops the indexed server listener. Another attempt waits for the selected client's callback state and indexed server state to reach Stopped. Shutdown starts outside the transport receive callback stack; Steam shuts down after transport teardown on application exit.
- A Steam lobby-full response or FishNet admission rejection can display a specific reason. A transport rejection before authentication remains a generic unavailable/full connection failure; no extra transport admission protocol is added.

## Gameplay decisions

- Spawn allocation uses the shared capacity and reuses released slots. **Timing deviation:** marker configuration is checked when the host starts loading Game, before player spawning. Markers are scene-owned, so checking them from MainMenu would require loading Game early or maintaining duplicate configuration. Missing markers end the session with a local host configuration error; guests may already have entered the lobby but are not individually rejected for missing spawn positions.
- Ordinary passenger requests require the current player revision, motion epoch, available destination, and no active handoff. Unrelated passenger revisions do not invalidate them. Driver changes and recovery retain the exact cart revision guard. Server order settles contested seats. Occupied, busy, and blocked results appear briefly in the HUD.
- Incident outcomes identify the reported motion epoch and sequence. Rejection releases only the matching pending incident, refreshes occupancy, and resets the rollover report latch for reassessment. Accepted incidents remain pending until the existing handoff/reset completes. Old revisions never apply reported rider velocities to a changed occupant set.
- Full inventory snapshots and operation outcomes go only to the owner, including spawn, selection, rejections, and seat permissions. Host owners apply them locally. World-item ownership/equipment and charging state remain public. No changed-slot protocol is introduced.
- Guest departure releases held records through the existing item lifecycle before FishNet destroys the player. Drops use the host's current player/seat pose and point velocity, with a vertical grid spaced using cached collider bounds to prevent mutual overlap. No final departure packet is required. Released records have no holder/equipped state and resume world simulation; whole-session teardown skips drops. Rejoining gets a fresh player and empty inventory.
- Rendering caps persist under `RenderingFrameCap` and set both FishNet render limits plus `Application.targetFrameRate`; v-sync is disabled. Network/physics simulation stays 60 Hz, item/cart motion stays approximately 20 Hz, and prediction/state forwarding remain unchanged.

## Required Unity assignments

1. Let Unity import the C# files and generate their metadata. Do not import the upstream SteamManager or a second Steamworks.NET copy.
2. On the existing `Assets/Game/Prefabs/SessionRoot.prefab`, add `SteamLifetime`, `SteamLobby`, `GameSteamTransport`, and FishNet `Multipass`. Keep the existing GameTransport and other session components.
3. Set Multipass **Transports** to the existing GameTransport at index 0 and GameSteamTransport at index 1. Keep that list stable, and disable **Global Server Actions**. Assign Multipass to **TransportManager → Transport**.
4. Assign **SessionController → Multipass**, **Local Transport**, and **Steam Transport** to those components. Keep its GameSettings assignment. GameSteamTransport must have **Peer To Peer** enabled and **Maximum Clients** set to 7; GameTransport's serialized default is 8, with IPv6/socket reuse still disabled. Runtime session capacity overrides both limits.
5. In `Assets/Scenes/Game.unity`, add six spawn-marker transforms and assign all eight to the existing GamePlayerSpawner. Use clear ground with enough separation for two-metre-tall, one-metre-wide player capsules and respawns. Solo uses the first marker. Extra markers beyond eight are ignored.
6. Save the prefab/scene and use the same content in every client build. Add the second existing GolfCart prefab instance later, as planned.
