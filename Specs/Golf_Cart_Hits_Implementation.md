# Golf cart hits: decisions and tuning

Shared predicted Rigidbody contact covers players and every observed cart. Unity supplies blocking, horizontal momentum transfer, and the cart's physical reaction. The pedestrian enhancement adds only upward velocity. PhysX and unknown remote input can still produce corrections; prediction does not guarantee identical contact timing across machines.

Paths below are relative to the repository root. Visual scenarios refer to section 14 of [Golf_Cart_Hits_v2_Plan.md](Golf_Cart_Hits_v2_Plan.md). Automated validation and profiling require separate authorization.

The parking estimates are analytical: `(240 - 150) / (450 * 0.75)` is approximately 0.27 m/s on flat ground, ignoring detailed tire/contact effects. A 150 N longitudinal resistance alone balances gravity for 450 kg at about two degrees. It cannot promise both easy pedestrian pushing and strong slope holding.

The launch targets are also analytical: an 8 m/s head-on impact against a stationary pedestrian targets 3.2 m/s upward, or about 0.52 m ideal ballistic rise; 15 m/s targets 6 m/s, or about 1.83 m. The solver, geometry, ground, and existing vertical speed affect the actual arc. Horizontal travel has no fixed multiplier.

## State and cost

`GolfCartNetwork.Prediction.cs` sends signed-byte steering/throttle, handbrake, generation, driver seat revision, and FishNet's managed replicate tick. Its reconcile state contains the prediction Rigidbody, generation/server tick, held controls and age, driven/parking/sleep flags, rear grip, settling duration, and fallback heading. Compression and ray hits are recomputed for active simulation; baseline display data initializes sleeping visuals. Crash, landing/stuck, rollover, and recovery-decision timers remain server-only. The baseline also carries current physical motion, controller state, input owner, and recovery origin; occupancy/cosmetics retain discrete RPCs.

`PlayerMotor.CartContacts.cs` uses an inline eight-entry value set so local history never references a mutable live contact collection. Its custom serializer writes only the active entries. Per-step contact arrays and overlap buffers are reused. Cart launch does not send a per-contact RPC or use the existing world-impact request protocol. `SessionController.Protocol` is `eight-player-birds-6`; the wire format and cart NetworkBehaviour layout require matching peers.

Cart input/reconcile follows the normal 60 Hz tick lifecycle, including local state capture at rest; the old 20 Hz transform publication stream is removed. Generation/revision fields make neutral input non-default to FishNet, so physics sleep does **not** imply network silence. Forwarded inputs, observer fan-out, Rigidbody state, and player contact state can cost more bandwidth than the previous stream. A later measured optimization could reduce idle transmission while retaining every required local history entry; suppressing history can cause FishNet to pause a necessary replay collision partner.

All observed carts simulate; the eight-player session limit is not a cart limit. Eight awake carts require 32 suspension rays per physics step, or 1,920 rays/second at 60 Hz before replay. With an average of `R` extra replay steps per forward tick, the estimate is `1,920 * (1 + R)` rays/second per machine. This excludes solver work, contact reconstruction/separation queries, history serialization, and observer traffic. Sleeping carts skip suspension queries. There is no continuous player-by-all-carts sweep; generation baseline installation is an occasional event that updates registered players.

For the section 14 several-carts/delay/loss scenarios, frame hitches or persistent correction oscillation justify separately authorized profiling of replay physics, contact queries, serialization, and bandwidth. These counts and tuning estimates are not profiling results.
